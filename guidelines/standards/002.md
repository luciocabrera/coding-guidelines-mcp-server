## 💻 Code Standard: Single Object Parameter for Multi-Argument Functions

### 🎯 Objective

To improve code readability, maintainability, and refactoring safety by ensuring all functions that accept **two or more arguments** are defined using a single destructured object parameter. This parameter must be typed using a dedicated, named `type` definition.

### 📜 Rule Details

1.  **Arguments Count:** This rule is mandatory for any function (including methods, arrow functions, and class methods) that accepts **two or more non-optional parameters**.
2.  **Destructuring:** The function signature must destructure the properties directly in the parameter list.
3.  **Named Type Required:** The parameter object **must** be typed using a distinct, non-inline `type` definition.
4.  **Type Naming Convention:**
    - For regular functions: The parameter type should be named after the function, suffixed with `Args` (e.g., `GetUserArgs`, `CalculateAreaArgs`).
      - ⚠️ **Never use `Arguments` suffix** - use `Args` instead
      - ✅ Correct: `ProcessDataArgs`, `ValidateInputArgs`
      - ❌ Wrong: `ProcessDataArguments`, `ValidateInputArguments`
    - **React Components:** The parameter type should be named after the component, suffixed with `Props` (e.g., `ButtonProps`, `CardProps`).
      - ⚠️ **Never use `Properties` suffix** - use `Props` instead
      - ✅ Correct: `ButtonProps`, `CardProps`
      - ❌ Wrong: `ButtonProperties`, `CardProperties`
5.  **Type File Organization:**
    - **Regular Functions/Utilities:** Type definitions should be placed directly above the function in the same file.
    - **React Components:** Type definitions (including props and all callback types) **must** be placed in a separate file named `ComponentName.types.ts` (e.g., `Button.types.ts` for `Button.tsx`).
6.  **Automated Enforcement:**
    - ESLint rule `local-rules/type-suffix-naming` enforces correct suffix usage
    - ESLint rule `local-rules/destructuring-for-functions` warns about missing destructuring

### ✅ Required Code Snippets (The "Do")

#### 1\. Regular Function/Utility Definition

For utility functions, keep type definitions in the same file, directly above the function.

```typescript
// ✅ DO: Define the type directly above the function in the same file
// File: process-tool-request.util.ts

type ProcessToolRequestArgs = {
  toolId: string;
  payload: Record<string, unknown>;
  timeoutMs: number;
};

const processToolRequest = ({
  toolId,
  payload,
  timeoutMs,
}: ProcessToolRequestArgs): Promise<void> => {
  console.log(`Processing tool ${toolId} with timeout ${timeoutMs}`);
  // ...
};
```

#### 2\. React Component with Separate Types File

For React components, all type definitions must be in a dedicated `.types.ts` file.

```typescript
// ✅ DO: Create a separate types file for the component
// File: Button.types.ts

export type ButtonProps = {
  label: string;
  variant?: 'primary' | 'secondary';
  onClick: (event: MouseEvent) => void;
  onHover?: (isHovered: boolean) => void;
};

// All callback parameter types should also be defined here
export type HandleSubmitArgs = {
  formData: FormData;
  validationRules: ValidationRule[];
};
```

```typescript
// ✅ DO: Import types from the separate types file
// File: Button.tsx

import type { ButtonProps } from './Button.types';

const Button = ({ label, onClick, variant = 'primary', onHover }: ButtonProps) => {
  const handleMouseEnter = () => {
    onHover?.(true);
  };

  return (
    <button
      className={variant}
      onClick={onClick}
      onMouseEnter={handleMouseEnter}
    >
      {label}
    </button>
  );
};

export default Button;
```

#### 3\. React Component with Internal Callbacks

When a component uses internal callbacks that accept multiple parameters, their types should also be defined in the `.types.ts` file.

```typescript
// ✅ DO: Define all callback types in the types file
// File: Form.types.ts

export type FormProps = {
  initialValues: Record<string, unknown>;
  onSubmit: (values: FormValues) => void;
};

// Internal callback types also belong here
export type HandleFieldChangeArgs = {
  fieldName: string;
  value: unknown;
  validate: boolean;
};

export type ValidateFieldArgs = {
  fieldName: string;
  value: unknown;
  rules: ValidationRule[];
};
```

```typescript
// ✅ DO: Import and use the types from the separate file
// File: Form.tsx

import type {
  FormProps,
  HandleFieldChangeArgs,
  ValidateFieldArgs
} from './Form.types';

const Form = ({ initialValues, onSubmit }: FormProps) => {
  const handleFieldChange = ({
    fieldName,
    value,
    validate
  }: HandleFieldChangeArgs) => {
    // Handle field change logic
  };

  const validateField = ({
    fieldName,
    value,
    rules
  }: ValidateFieldArgs): boolean => {
    // Validation logic
    return true;
  };

  return <form>{/* Form content */}</form>;
};
```

#### 4\. Function Call Site

```typescript
const toolPayload = { data: 'config' };
const toolTimeout = 5000;

// ✅ DO: Call the function using a single object (Order doesn't matter)
processToolRequest({
  timeoutMs: toolTimeout,

```

### ❌ Forbidden Code Snippets (The "Don't")

#### 1\. Multiple Positional Arguments

Using multiple arguments is prohibited as it is fragile and difficult to read when called.

```typescript
// ❌ DON'T: Use multiple positional arguments
const calculateArea = (height: number, width: number): number => {
  return height * width;
};

// ❌ DON'T: Call order matters and is unclear without parameter names
calculateArea(10, 20); // Which is height? Which is width?
```

#### 2\. Inline Type Definition

Using an object parameter without a named `type` definition is prohibited, as it makes documentation and refactoring difficult.

```typescript
// ❌ DON'T: Use an inline type definition (even with destructuring)
const saveConfig = ({ id, data }: { id: string; data: object }): void => {
  // ...
};

// ❌ DON'T: Use inline type for React components
const Card = ({ title, content }: { title: string; content: string }) => {
  return <div>{title}</div>;
};
```

#### 3\. Types Defined in Component File

For React components, types must be in a separate `.types.ts` file, not in the component file itself.

```typescript
// ❌ DON'T: Define types in the component file
// File: Button.tsx

type ButtonProps = {  // This should be in Button.types.ts
  label: string;
  onClick: () => void;
};

const Button = ({ label, onClick }: ButtonProps) => {
  return <button onClick={onClick}>{label}</button>;
};
```

#### 4\. Callback Types Missing from Types File

Internal callback types should also be defined in the `.types.ts` file, not inline in the component.

```typescript
// ❌ DON'T: Define callback types inline in the component file
// File: Form.tsx

import type { FormProps } from './Form.types';

const Form = ({ initialValues, onSubmit }: FormProps) => {
  // ❌ DON'T: This type should be in Form.types.ts
  const handleFieldChange = ({
    fieldName,
    value
  }: { fieldName: string; value: unknown }) => {
    // ...
  };

  return <form>{/* Form content */}</form>;
};
```

#### 5\. Utility Functions with Separate Types Files

For utility functions, types should not be in separate files (unless they're shared across multiple utilities).

```typescript
// ❌ DON'T: Create a separate types file for simple utilities
// File: process-tool-request.types.ts
export type ProcessToolRequestArgs = {
  toolId: string;
  payload: Record<string, unknown>;
};

// File: process-tool-request.util.ts
import type { ProcessToolRequestArgs } from './process-tool-request.types';
// This adds unnecessary file overhead for non-component code
```

#### 6\. Undestructured Object Parameter

Accepting an object without immediate destructuring is discouraged because it creates unnecessary variable prefixing.

```typescript
// ❌ DON'T: Accept the object without immediate destructuring
type SaveConfigArgs = { id: string; data: object };
const saveConfig = (params: SaveConfigArgs): void => {
  console.log(params.id); // Verbose and adds unnecessary indirection
};
```

#### 7\. Wrong Naming Convention for React Components

Using the `Args` suffix for React component props types is incorrect and violates React conventions.

```typescript
// ❌ DON'T: Use 'Args' suffix for React component props
type ButtonArgs = {
  // Should be ButtonProps
  label: string;
  onClick: () => void;
};
```

#### 8\. Wrong Types File Naming

The types file must follow the `ComponentName.types.ts` naming convention.

```typescript
// ❌ DON'T: Use incorrect naming for types file
// File: ButtonTypes.ts (WRONG)
// File: button.types.ts (WRONG - casing doesn't match component)
// File: Button-types.ts (WRONG - use dot notation)

// ✅ DO: Use correct naming
// File: Button.types.ts (CORRECT)
```

### 📝 Summary of Dos and Don'ts

#### ✅ DO:

- Use a single destructured object parameter for functions with 2+ arguments
- Create dedicated, named type definitions (never inline)
- Use `Args` suffix for regular functions (e.g., `ProcessToolRequestArgs`)
- Use `Props` suffix for React components (e.g., `ButtonProps`)
- Place utility function types directly above the function in the same file
- Place React component types in a separate `ComponentName.types.ts` file
- Include all callback types used within a component in its `.types.ts` file
- Destructure parameters directly in the function signature
- Call functions using named object properties for clarity

#### ❌ DON'T:

- Use multiple positional parameters (2 or more)
- Define types inline in the parameter list
- Accept parameters without immediate destructuring
- Define React component types in the component file itself
- Define callback types inline within React components
- Create separate type files for simple utility functions
- Use `Args` suffix for React component props types
- Use `Props` suffix for non-React functions
- Use incorrect naming conventions for types files (must be `ComponentName.types.ts`)
- Omit type definitions entirely

### 🎯 Quick Reference: Where to Put Types

| Code Type             | Type Location                     | Type Suffix | Example                                                    |
| --------------------- | --------------------------------- | ----------- | ---------------------------------------------------------- |
| Utility Function      | Same file, above function         | `Args`      | `ProcessToolRequestArgs` in `process-tool-request.util.ts` |
| React Component Props | Separate `ComponentName.types.ts` | `Props`     | `ButtonProps` in `Button.types.ts`                         |
| Component Callbacks   | Separate `ComponentName.types.ts` | `Args`      | `HandleSubmitArgs` in `Form.types.ts`                      |
| Shared Types          | Dedicated types file/folder       | Varies      | `types/common.ts`                                          |
