## 💻 Code Standard: Type-Safe Template Literal Expressions

### 🎯 Objective

To ensure type safety and prevent runtime errors in template literals by requiring explicit type conversion for values that may not have a reliable string representation. This standard enforces that only string-like types are used directly in template literals, while numbers and complex types are explicitly converted using appropriate methods. This prevents unexpected `[object Object]` strings and ensures predictable string concatenation behavior.

### 📜 Rule Details

1.  **Allowed Types:** Only the following types can be used directly in template literal expressions without conversion:
    - `string`
    - `boolean` (converts to `"true"` or `"false"`)
    - `null` (converts to `"null"`)
    - `undefined` (converts to `"undefined"`)

2.  **Numbers Require Conversion:** All numeric types (`number`, `bigint`) must be explicitly converted to strings using `.toString()` or `String()` before use in template literals.

3.  **Objects Require Conversion:** Complex types (objects, arrays, custom types) must be:
    - Converted using `JSON.stringify()` for serialization
    - Converted using specific property access for single values
    - Converted using custom `.toString()` methods when available
    - Converted using `String()` only when the type guarantees a meaningful string representation

4.  **Error Types:** When working with errors in template literals, access specific properties like `error.message` or use type guards to ensure proper string conversion.

5.  **Type Safety First:** Prefer accessing specific string properties over generic `.toString()` or `String()` conversions when dealing with complex types.

### ✅ Required Code Snippets (The "Do")

#### 1\. Converting Numbers in Template Literals

Always explicitly convert numbers to strings using `.toString()` or `String()`.

```typescript
// ✅ DO: Explicitly convert numbers to strings
// File: format-message.util.ts

type FormatMessageArgs = {
  username: string;
  count: number;
  lineNumber: number;
};

export const formatMessage = ({ username, count, lineNumber }: FormatMessageArgs): string => {
  // Use .toString() for number conversion
  const message = `User ${username} has ${count.toString()} items`;

  // Alternative: Use String() for conversion
  const lineInfo = `Error on line ${String(lineNumber)}`;

  return `${message}. ${lineInfo}`;
};
```

```typescript
// ✅ DO: Convert numbers in template literals for logging
// File: logger.util.ts

type LogProgressArgs = {
  current: number;
  total: number;
  percentage: number;
};

export const logProgress = ({ current, total, percentage }: LogProgressArgs): void => {
  console.log(
    `Processing ${current.toString()} of ${total.toString()} (${percentage.toString()}%)`,
  );
};
```

#### 3\. Type Guards for Unknown Types

Use type guards when dealing with unknown or any types.

```typescript
// ✅ DO: Use type guards before template literal usage
// File: safe-stringify.util.ts

const isStringifiable = (value: unknown): value is { toString(): string } => {
  return value !== null && value !== undefined && typeof value === 'object' && 'toString' in value;
};

type SafeStringifyArgs = {
  value: unknown;
  fallback?: string;
};

export const safeStringify = ({ value, fallback = 'N/A' }: SafeStringifyArgs): string => {
  if (typeof value === 'string') {
    return value;
  }

  if (typeof value === 'number' || typeof value === 'boolean') {
    return String(value);
  }

  if (isStringifiable(value)) {
    return value.toString();
  }

  return fallback;
};
```

#### 4\. Array Indices and Counts

Convert numeric array indices and counts to strings.

```typescript
// ✅ DO: Convert array indices to strings

type SearchMatch = {

type FormatSearchResultsArgs = {

export const formatSearchResults = ({ matches }: FormatSearchResultsArgs): string => {
  return matches
    .map(({ line, index }) => {
      // Convert index to string explicitly
      return `Line ${(index + 1).toString()}: ${line}`;

    .join('\n');
```
```typescript
};
```

#### 5\. Error Handling in Template Literals

Access error properties safely or use type guards.

```typescript

};

export const handleError = ({ error, operation }: HandleErrorArgs): string => {
```

### ❌ Anti-Patterns (The "Don't")

#### 1\. Using Numbers Directly in Template Literals

```typescript
// ❌ DON'T: Use numbers directly without conversion
// File: format-message.util.ts (WRONG)

type FormatMessageArgs = {
  count: number;
  lineNumber: number;
};

export const formatMessage = ({ count, lineNumber }: FormatMessageArgs): string => {
  // ❌ Numbers used directly - violates type safety
  return `Found ${count} items on line ${lineNumber}`;
};
```

**Why it's wrong:**

- Violates `@typescript-eslint/restrict-template-expressions` rule
- Implicit conversion can hide type issues
- Makes type safety less explicit

**How to fix:**

```typescript
// ✅ CORRECT: Explicitly convert numbers
export const formatMessage = ({ count, lineNumber }: FormatMessageArgs): string => {
  return `Found ${count.toString()} items on line ${lineNumber.toString()}`;
};
```

#### 2\. Using Objects Directly in Template Literals

```typescript
// ❌ DON'T: Use objects directly in template literals
// File: log-request.util.ts (WRONG)

type LogRequestArgs = {
  request: Request;
  payload: Record<string, unknown>;
};

export const logRequest = ({ request, payload }: LogRequestArgs): void => {
  // ❌ Object used directly - will produce "[object Object]"
  console.log(`Request: ${request}, Payload: ${payload}`);
};
```

**Why it's wrong:**

- Results in unhelpful `"[object Object]"` strings
- Loses all useful information
- Violates type safety rules

**How to fix:**

```typescript
// ✅ CORRECT: Access specific properties or use JSON.stringify
export const logRequest = ({ request, payload }: LogRequestArgs): void => {
  console.log(`Request: ${request.url}, Payload: ${JSON.stringify(payload)}`);
};
```

#### 3\. Using Type Parameters Directly

```typescript
// ❌ DON'T: Use complex type parameters directly
// File: create-error.util.ts (WRONG)

type CreateErrorArgs<T> = {
  data: T;
  operation: string;
};

export const createError = <T>({ data, operation }: CreateErrorArgs<T>): Error => {
  // ❌ Generic type parameter used directly
  return new Error(`Failed ${operation} with data: ${data}`);
};
```

**Why it's wrong:**

- Type parameter `T` could be any type
- No guarantee of meaningful string conversion
- Violates type safety requirements

**How to fix:**

```typescript
// ✅ CORRECT: Use JSON.stringify or require string property
export const createError = <T>({ data, operation }: CreateErrorArgs<T>): Error => {
  return new Error(`Failed ${operation} with data: ${JSON.stringify(data)}`);
};

// ✅ OR: Constrain the generic type
type CreateErrorArgs<T extends { toString(): string }> = {
  data: T;
  operation: string;
};

export const createError = <T extends { toString(): string }>({
  data,
  operation,
}: CreateErrorArgs<T>): Error => {
  return new Error(`Failed ${operation} with data: ${data.toString()}`);
};
```

#### 4\. Using Unknown Error Types Directly

```typescript
// ❌ DON'T: Use unknown error types directly
// File: handle-error.util.ts (WRONG)

type HandleErrorArgs = {
  error: unknown;
  context: string;
};

export const handleError = ({ error, context }: HandleErrorArgs): void => {
  // ❌ Unknown type used directly
  console.error(`Error in ${context}: ${error}`);
};
```

**Why it's wrong:**

- `error` could be anything (object, number, null, etc.)
- No type safety guarantee
- May produce unhelpful error messages

**How to fix:**

```typescript
// ✅ CORRECT: Use type guards and access specific properties
export const handleError = ({ error, context }: HandleErrorArgs): void => {
  if (error instanceof Error) {
    console.error(`Error in ${context}: ${error.message}`);
  } else if (typeof error === 'string') {
    console.error(`Error in ${context}: ${error}`);
  } else {
    console.error(`Error in ${context}: ${JSON.stringify(error)}`);
  }
};
```

#### 5\. Using Array Indices Without Conversion

```typescript
// ❌ DON'T: Use numeric indices directly
// File: format-list.util.ts (WRONG)

type FormatListArgs = {
  items: string[];
};

export const formatList = ({ items }: FormatListArgs): string => {
  return items
    .map((item, index) => {
      // ❌ Numeric index used directly
      return `${index + 1}. ${item}`;
    })
    .join('\n');
};
```

**Why it's wrong:**

- Violates explicit type conversion requirement
- Less clear about type handling

**How to fix:**

```typescript
// ✅ CORRECT: Convert index to string explicitly
export const formatList = ({ items }: FormatListArgs): string => {
  return items
    .map((item, index) => {
      return `${(index + 1).toString()}. ${item}`;
    })
    .join('\n');
};
```

### 📋 Common Conversion Methods

| Type        | Recommended Method              | Example               |
| ----------- | ------------------------------- | --------------------- |
| `number`    | `.toString()` or `String()`     | `count.toString()`    |
| `bigint`    | `.toString()` or `String()`     | `bigNum.toString()`   |
| `Error`     | Access `.message`               | `error.message`       |
| `Object`    | `JSON.stringify()`              | `JSON.stringify(obj)` |
| `Array`     | `JSON.stringify()` or `.join()` | `arr.join(', ')`      |
| `unknown`   | Type guard + specific handling  | See example above     |
| Custom type | Access string properties        | `user.name`           |

### 🎯 Summary

- **Always** explicitly convert numbers using `.toString()` or `String()`
- **Always** access specific string properties from objects instead of using the whole object
- **Always** use `JSON.stringify()` when you need full object serialization
- **Always** use type guards when dealing with `unknown` or `any` types
- **Never** use complex types directly in template literals without conversion
- **Never** rely on implicit `.toString()` calls for objects
