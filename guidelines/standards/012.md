## 💻 Code Standard: No Unnecessary Conditionals

### 🎯 Objective

To prevent unnecessary conditional expressions that are always truthy or always falsy based on TypeScript's type analysis. These conditions indicate either dead code, incorrect type assumptions, or redundant checks that should be removed to improve code clarity and maintainability.

### 📜 Rule Details

1.  **Eliminate Always-Truthy Conditions:** Remove conditional expressions that TypeScript determines will always evaluate to `true`.

2.  **Eliminate Always-Falsy Conditions:** Remove conditional expressions that TypeScript determines will always evaluate to `false`.

3.  **Trust Type System:** If TypeScript's type system guarantees a value cannot be `null` or `undefined`, don't check for it.

4.  **Remove Redundant Guards:** After narrowing types through proper type guards, don't add redundant null checks.

5.  **Fix Type Issues First:** If a condition seems necessary but TypeScript says it's unnecessary, the root cause is usually an incorrect type definition or missing null check upstream.

### 🔍 Why This Matters

Unnecessary conditionals are problematic because they:

- **Hide bugs**: Code that can never execute might contain errors that won't be caught
- **Create confusion**: Developers reading the code may assume the condition can be false
- **Indicate type errors**: Often signal incorrect type definitions or missing type guards elsewhere
- **Add noise**: Make code harder to read without adding value
- **Reduce trust**: If some "safety checks" are unnecessary, which ones actually matter?

### ✅ Required Code Snippets (The "Do")

#### 1\. Remove Always-Falsy Checks

When TypeScript's type analysis proves a value cannot be null/undefined, don't check for it.

```typescript
// ✅ DO: Trust TypeScript's type narrowing
// File: user-service.ts

type User = {
  id: string;
  name: string;
  email: string;
};

type GetUserDisplayArgs = {
  user: User;
};

export const getUserDisplay = ({ user }: GetUserDisplayArgs): string => {
  // User is never null/undefined per type definition
  return `${user.name} (${user.email})`;
};
```

```typescript
// ✅ DO: Use proper type narrowing instead of redundant checks
// File: process-items.ts

type ProcessItemsArgs = {
  items: string[];
};

export const processItems = ({ items }: ProcessItemsArgs): number => {
  // items is string[], so it's never null/undefined
  return items.length;
};
```

#### 2\. Fix Type Definitions Instead of Adding Checks

When you feel you need a null check, make the type reflect reality.

```typescript
// ✅ DO: Reflect optionality in types
// File: format-user.ts

type FormatUserArgs = {
  user: User | undefined; // Type reflects that user might be undefined
};

export const formatUser = ({ user }: FormatUserArgs): string => {
  // Now this check is necessary and not flagged
  if (!user) {
    return 'No user';
  }
  return user.name;
};
```

```typescript
// ✅ DO: Use optional chaining when property might not exist
// File: get-config-value.ts

type Config = {
  settings?: {
    theme?: string;
  };
};

type GetThemeArgs = {
  config: Config;
};

export const getTheme = ({ config }: GetThemeArgs): string => {
  // Optional chaining handles the optionality
  return config.settings?.theme ?? 'default';
};
```

#### 3\. After Type Guards, Trust the Narrowing

Once TypeScript narrows a type, don't add redundant checks.

```typescript
// ✅ DO: Trust type narrowing after guards
// File: process-value.ts

type ProcessValueArgs = {
  value: string | number | undefined;
};

export const processValue = ({ value }: ProcessValueArgs): string => {
  if (value === undefined) {
    return 'empty';
  }

  // After the guard, value is string | number (never undefined)
  // No need to check for undefined again
  if (typeof value === 'string') {
    return value.toUpperCase();
  }

  return value.toString();
};
```

#### 4\. Handle Array/Object Validation Correctly

Use proper existence checks, not redundant ones.

```typescript
// ✅ DO: Check array length, not array itself if type guarantees it exists
// File: process-list.ts

type ProcessListArgs = {
  items: string[]; // Type guarantees array exists
};

export const processFirst = ({ items }: ProcessListArgs): string | undefined => {
  // Check length, not existence of array
  if (items.length === 0) {
    return undefined;
  }

  return items[0];
};
```

```typescript
// ✅ DO: Use .at() for safe array access
// File: get-item.ts

type GetItemArgs = {
  items: string[];
  index: number;
};

export const getItem = ({ items, index }: GetItemArgs): string | undefined => {
  // .at() returns undefined for invalid indices, no need for length check
  return items.at(index);
};
```

### ❌ Forbidden Code Snippets (The "Don't")

#### 1\. Don't Check Non-Nullable Values

```typescript
// ❌ DON'T: Check for null when type guarantees non-null
// File: bad-user-service.ts

type User = {
  id: string;
  name: string;
};

export const getUserName = (user: User): string => {
  // WRONG: user is never null per type definition
  if (!user) {
    return 'Unknown';
  }
  return user.name;
};
```

#### 2\. Don't Add Redundant Guards After Type Narrowing

```typescript
// ❌ DON'T: Check again after type narrowing
// File: bad-validator.ts

export const validateInput = (input: string | undefined): boolean => {
  if (!input) {
    return false;
  }

  // WRONG: input is definitely string here, no need to check again
  if (!input) {
    return false;
  }

  return input.length > 0;
};
```

#### 3\. Don't Check Array Existence When Type Guarantees It

```typescript
// ❌ DON'T: Check if array exists when type says it always does
// File: bad-array-handler.ts

type ProcessArgs = {
  items: string[];
};

export const process = ({ items }: ProcessArgs): number => {
  // WRONG: items is always an array per type definition
  if (!items) {
    return 0;
  }

  return items.length;
};
```

#### 4\. Don't Check After Object.hasOwn Validation

```typescript
// ❌ DON'T: Add redundant null check after validation
// File: bad-object-access.ts

const RULES: Record<string, string[]> = {
  typescript: ['rule1', 'rule2'],
};

export const getRules = (category: string): string[] | undefined => {
  if (!Object.hasOwn(RULES, category)) {
    return undefined;
  }

  const rules = RULES[category];

  // WRONG: rules cannot be null/undefined after Object.hasOwn check
  if (!rules) {
    return undefined;
  }

  return rules;
};
```

### 📋 Validation Checklist

Before committing code, verify:

- [ ] No conditionals that check for `null`/`undefined` on non-nullable types
- [ ] No redundant checks after type narrowing guards
- [ ] Types accurately reflect optionality (use `T | undefined` when needed)
- [ ] Array/object checks validate the right property (length/keys, not existence)
- [ ] After using `Object.hasOwn()`, no additional null checks on the property
- [ ] No dead code branches that can never execute
- [ ] TypeScript's strict type checking enabled and passing

### 🎯 Summary

**Always trust TypeScript's type system.** If the type says a value cannot be `null` or `undefined`, don't check for it. If you feel the need to check, the type definition is wrong—fix the type instead of adding unnecessary conditionals. This makes code clearer, eliminates dead code, and ensures types accurately document the code's behavior.

### 🔧 Automated Enforcement

- **ESLint Rule:** `@typescript-eslint/no-unnecessary-condition`
- **Configuration:** Enabled as error in `eslint.config.mjs`
- **Auto-fix:** Not available (requires manual code analysis)
- **TypeScript:** Requires `strictNullChecks: true` in `tsconfig.json`
