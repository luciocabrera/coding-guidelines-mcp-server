## 💻 Code Standard: Boolean Naming Conventions

### 🎯 Objective

To establish clear and consistent naming conventions for boolean variables, properties, and function return types. Proper boolean naming makes code self-documenting, improves readability, and eliminates ambiguity about what a variable represents. Boolean names should read naturally in conditional statements and clearly indicate their true/false nature.

### 📜 Rule Details

1.  **Required Prefixes:** All boolean variables, object properties, type properties, and function returns must use one of the following prefixes:
    - `is` - Indicates a state or condition (most common)
    - `has` - Indicates possession or presence of something
    - `can` - Indicates ability or permission
    - `should` - Indicates recommendation or expectation
    - `will` - Indicates future action or intent
    - `did` - Indicates past action or completion
    - `was` - Indicates past state
    - `are` - Indicates plural state
    - `includes` - Indicates inclusion or containment
    - `enables` - Indicates activation or enablement

2.  **Naming Pattern:** Boolean names should follow the pattern `prefix + descriptor` where the descriptor clearly explains what is being checked (e.g., `isVisible`, `hasPermission`, `canEdit`).

3.  **Natural Reading:** Names should read naturally in if statements: `if (isVisible)`, `if (hasAccess)`, `if (canDelete)`.

4.  **Avoid Negatives:** Prefer positive boolean names over negative ones (use `isEnabled` instead of `isDisabled` when possible).

5.  **Consistent Tense:** Use consistent verb tense within related booleans (all present tense or all past tense).

  shouldTrim: boolean;
  shouldRemoveSpecialChars: boolean;

export const formatText = ({
  text,
  shouldCapitalize,
  shouldTrim,
  shouldRemoveSpecialChars,
}: FormatTextArgs): string => {
  let result = text;

  if (shouldTrim) {
    result = result.trim();
  }

  if (shouldRemoveSpecialChars) {
    result = result.replace(/[^a-zA-Z0-9\s]/g, '');
  }

  if (shouldCapitalize) {
    result = result.charAt(0).toUpperCase() + result.slice(1);
  }

  return result;
};

type ValidationResult = {
  isValid: boolean;
  hasErrors: boolean;
  errors: string[];

export const validatePassword = (password: string): ValidationResult => {
  const errors: string[] = [];

  const hasMinLength = password.length >= 8;
  const hasUpperCase = /[A-Z]/.test(password);
  const hasLowerCase = /[a-z]/.test(password);
  const hasNumber = /\d/.test(password);
  const hasSpecialChar = /[@$!%*?&]/.test(password);

  if (!hasMinLength) errors.push('Password must be at least 8 characters');
  if (!hasUpperCase) errors.push('Password must contain an uppercase letter');
  if (!hasLowerCase) errors.push('Password must contain a lowercase letter');
  if (!hasNumber) errors.push('Password must contain a number');
  if (!hasSpecialChar) errors.push('Password must contain a special character');

  return {
    isValid: errors.length === 0,
    hasErrors: errors.length > 0,
    errors,
  };
};

#### 5\. State Variables with Booleans

```typescript
// ✅ DO: Use proper prefixes for state variables
// File: LoginForm.tsx

import { useState } from 'react';
import type { LoginFormProps } from './LoginForm.types';

export const LoginForm = ({ onSubmit }: LoginFormProps) => {
  const [email, setEmail] = useState('');
  const [password, setPassword] = useState('');
  const [isLoading, setIsLoading] = useState(false);
  const [isPasswordVisible, setIsPasswordVisible] = useState(false);
  const [hasAcceptedTerms, setHasAcceptedTerms] = useState(false);
  const [shouldRememberMe, setShouldRememberMe] = useState(false);
  const [wasSubmitted, setWasSubmitted] = useState(false);

  const handleSubmit = async (event: React.FormEvent) => {
    event.preventDefault();
    setIsLoading(true);
    setWasSubmitted(true);

    try {
      await onSubmit({ email, password, shouldRememberMe });
    } finally {
      setIsLoading(false);
    }
  };

  const handleTogglePasswordVisibility = () => {
    setIsPasswordVisible((prev) => !prev);
  };

  const canSubmit = email && password && hasAcceptedTerms && !isLoading;

  return (
    <form onSubmit={handleSubmit}>
      <input
        type="email"
        value={email}
        onChange={(e) => setEmail(e.target.value)}
        placeholder="Email"
        disabled={isLoading}
      />

      <div>
        <input
          type={isPasswordVisible ? 'text' : 'password'}
          value={password}
          onChange={(e) => setPassword(e.target.value)}
          placeholder="Password"
          disabled={isLoading}
        />
        <button type="button" onClick={handleTogglePasswordVisibility}>
          {isPasswordVisible ? 'Hide' : 'Show'}
        </button>
      </div>

      <label>
        <input
          type="checkbox"
          checked={hasAcceptedTerms}
          onChange={(e) => setHasAcceptedTerms(e.target.checked)}
          disabled={isLoading}
        />
        I accept the terms and conditions
      </label>

      <label>
        <input
          type="checkbox"
          checked={shouldRememberMe}
          onChange={(e) => setShouldRememberMe(e.target.checked)}
          disabled={isLoading}
        />
        Remember me
      </label>

      <button type="submit" disabled={!canSubmit}>
        {isLoading ? 'Logging in...' : 'Login'}
      </button>

      {wasSubmitted && <p>Form was submitted</p>}
    </form>
  );
};
```

type CheckUserAccessArgs = {

  resourceId: string;
  requiredPermission: string;

export const checkUserAccess = ({
  userId,
  resourceId,
  requiredPermission,
}: CheckUserAccessArgs): boolean => {
  const user = getUserById(userId);
  const resource = getResourceById(resourceId);

  const isUserActive = user.status === 'active';
  const isUserBanned = user.status === 'banned';
  const isResourcePublic = resource.visibility === 'public';
  const isUserOwner = resource.ownerId === userId;
  const hasRequiredPermission = user.permissions.includes(requiredPermission);
  const isUserAdmin = user.role === 'admin';

  // Clear logic flow with well-named booleans

    return false;
  }

  if (!isUserActive) {
    return false;
  }

  if (isResourcePublic) {
    return true;
  }

  if (isUserOwner || isUserAdmin) {
    return true;
  }

  return hasRequiredPermission;
};

### 📝 Summary of Dos and Don'ts

#### ✅ DO:

**General Rules**

- Always use proper prefixes: `is`, `has`, `can`, `should`, `will`, `did`, `was`, `are`, `includes`, `enables`
- Make boolean names read naturally in if statements
- Use descriptive names that clearly indicate what is being checked
- Prefer positive boolean names over negative ones (when it makes sense)
- Be consistent with prefixes for related booleans
- Use `as const` for object constants with boolean values

**Specific Prefixes**

- Use `is` for states and conditions (`isVisible`, `isActive`, `isLoading`)
- Use `has` for possession or presence (`hasPermission`, `hasErrors`, `hasAvatar`)
- Use `can` for abilities and permissions (`canEdit`, `canDelete`, `canAccess`, `canComment`)
- Use `should` for recommendations or expectations (`shouldValidate`, `shouldNotify`)
- Use `will` for future actions (`willExpire`, `willUpdate`)
- Use `did` for completed actions (`didComplete`, `didSubmit`)
- Use `was` for past states (`wasActive`, `wasVerified`)
- Use `are` for plural states (`areAllSelected`, `areFilesUploaded`)
- Use `includes` for inclusion (`includesVAT`, `includesShipping`)
- Use `enables` for enablement (`enablesFeature`, `enablesAccess`)

**Context-Specific Usage**

- Component props: Use prefixes that make sense for UI state
- Function parameters: Use `should` for options that control behavior
- Return values: Match the prefix to what the function checks
- State variables: Use prefixes that indicate current state
- Config values: Use prefixes that indicate settings or features

#### ❌ DON'T:

- Don't omit boolean prefixes from variable, property, or function names
- Don't use ambiguous names that don't clearly indicate boolean nature
- Don't mix positive and negative boolean naming inconsistently
- Don't use verbs without proper prefixes (`active`, `visible`, `enabled`)
- Don't use nouns as boolean names (`notifications`, `avatar`, `profile`)
- Don't create double-negative logic with negative boolean names
- Don't be inconsistent with prefix usage for related booleans
- Don't use unclear abbreviations in boolean names
- Don't forget prefixes in type definitions and interfaces
- Don't use different prefixes for the same concept across the codebase

### 🎯 Quick Reference: Boolean Prefix Usage

| Prefix     | Use Case                   | Examples                                                       | When to Use                      |
| ---------- | -------------------------- | -------------------------------------------------------------- | -------------------------------- |
| `is`       | State or condition         | `isVisible`, `isActive`, `isLoading`, `isPremium`              | Most common prefix for states    |
| `has`      | Possession/presence        | `hasPermission`, `hasError`, `hasAvatar`, `hasChildren`        | When checking for existence      |
| `can`      | Ability/permission         | `canEdit`, `canDelete`, `canAccess`, `canSubmit`, `canComment` | For permissions and capabilities |
| `should`   | Recommendation/expectation | `shouldValidate`, `shouldNotify`, `shouldRender`               | For behavior options             |
| `will`     | Future action/intent       | `willExpire`, `willUpdate`, `willNotify`                       | For future states                |
| `did`      | Past action/completion     | `didComplete`, `didSubmit`, `didLoad`                          | For completed actions            |
| `was`      | Past state                 | `wasActive`, `wasVerified`, `wasPublished`                     | For historical states            |
| `are`      | Plural state               | `areAllSelected`, `areValid`, `areEnabled`                     | For plural conditions            |
| `includes` | Inclusion/containment      | `includesVAT`, `includesShipping`, `includesDiscount`          | For inclusion checks             |
| `enables`  | Activation/enablement      | `enablesFeature`, `enablesAccess`, `enablesEditing`            | For feature toggles              |

### 🔍 Decision Tree: Which Prefix Should I Use?

```
What does this boolean represent?

├─ A current state or condition?
│  └─ Use `is` (isActive, isVisible, isLoading)
│
├─ Possession or presence of something?
│  └─ Use `has` (hasPermission, hasError, hasData)
│
├─ An ability or permission?
│  └─ Use `can` (canEdit, canDelete, canAccess, canComment)
│
├─ A recommendation or expected behavior?
│  └─ Use `should` (shouldValidate, shouldNotify)
│
├─ A future action or intent?
│  └─ Use `will` (willExpire, willUpdate)
│
├─ A completed past action?
│  └─ Use `did` (didComplete, didSubmit)
│
├─ A historical state?
│  └─ Use `was` (wasActive, wasVerified)
│
├─ A plural or collective state?
│  └─ Use `are` (areAllSelected, areValid)
│
├─ Inclusion or containment?
│  └─ Use `includes` (includesVAT, includesShipping)
│
└─ Feature activation or enablement?
   └─ Use `enables` (enablesFeature, enablesAccess)
```
